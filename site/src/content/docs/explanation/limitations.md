---
title: Limitations
description: What this build does not do.
---

These are product limits, not temporary bugs.

- Vault KV v2 only. KV v1, dynamic credentials, transit, and PKI are not exposed.
- `ensure` without `#field` treats an existing Vault path as present. It does not add a missing `value` field and it does not undelete a soft-deleted secret.
- A lost Vault CAS race is not retried with an unconditional write.
- Infisical `ensure` sends only the v4 Create (`POST`); it does not check for absence first. In v0.167.11 the server enforces a partial unique index on (`key`, `folderId`) for shared secrets, so a duplicate insert cannot replace the existing row. A sequential duplicate is HTTP `400` and is reported `present`; a create that loses a concurrent insert race is an error (observed as HTTP `500`), never a silent update or a `present` result. A `200` Create response must be the documented object, with a non-empty id, the requested key, project, environment, and shared type; a malformed, empty, or mismatched object is a redacted error, not `created`.
- Infisical list is one folder, `recursive = false`, and is not paginated.
- KeePass can `set` only an entry's `Password`, on stdin. Other attributes are read-only because `keepassxc-cli edit` takes them in `argv`. New entries require an existing parent group. `ensure` is refused: the CLI's check followed by `add` is not atomic against an external writer, and its observed duplicate refusal is not a documented conditional create. KeePass writes share one lock identity across every database on the machine because hard links and atomic file replacement make a path or inode identity unsafe. External tools that do not take that lock can still lose a concurrent change.
- Proton stays read-only because the documented update takes the value in `argv`, and there is no atomic create-if-absent operation. Vaultwarden can `set` through `bw create item`/`bw edit item`; its `ensure` is refused because the CLI cannot create conditionally.
- Vaultwarden list uses `bw list items`, which returns full items. The adapter keeps names and must not return the password from `ls`.
- Proton list is not a metadata-only fetch. In `pass-cli` 2.7.1, `item list --output json` downloads and decrypts each item before serializing a summary without content. The adapter keeps only titles, but the CLI process did fetch the item bodies. A configured token uses a private per-process session directory under a verified temporary parent, and the adapter requires `info --output json` to identify a personal access token before it reads anything. `list` and `get` on one provider instance are serialized. The directory is removed on drop; a failed removal prints a warning and leaves it for the system to clean, and a killed process cannot run cleanup. Token mode fails closed on platforms without the hardened directory walk, or when the temporary path is not a trusted, symlink-free location.
- Vaultwarden writes take a shared lock and run `bw sync` (failing closed) before the whole-item read-modify-write, so two CLI state directories can update one item without losing a field. Reads use the local copy and can be stale. Concurrent external clients are not coordinated: the CLI sends `lastKnownRevisionDate` and the server can reject a change that lands after the sync, but a change before the sync is incorporated, a server without the check or an update inside the one-second window can still lose a concurrent change. nsvault does not preserve concurrent external changes.
- GitHub cannot `get` or `ensure`. Repository Actions secrets only.
- Vault/OpenBao `set`/`ensure`, GitHub `set`, Infisical `set`/`ensure`, AWS Secrets Manager `set`/`ensure`, GCP Secret Manager `set`, Azure Key Vault `set`, Vaultwarden `set`, and KeePass `set` use a Linux `flock` same-user lock in `$XDG_STATE_HOME/nsvault/locks` or `NSVAULT_LOCK_DIR` (Vaultwarden shares one identity across every profile on the machine, because wrapper paths differ; KeePass shares one identity across every KDBX file on the machine, because hard links and file replacement make a path or inode identity unsafe; AWS, GCP, and Azure derive the identity from the endpoint and, for AWS, the region, rather than the profile or credentials). The path must be absolute and no component may be a symlink. An existing directory is never chmodded; a foreign owner, group/world-accessible directory, or a parent not owned by root or this user is refused, and a writable parent must also be sticky. The lock is advisory: removing, renaming, or replacing the lock file or directory breaks it, so it is not a same-user security boundary. It does not stop the Vault CLI, another host, or another OS user. Windows and macOS were not exercised.
- No `remove`. No daemon, cache, keyring, or local encrypted store.
- No `import` and no `export`. An age file is not a nsvault backup.
- No request-rewriting proxy and no placeholder syntax. `exec` does not edit HTTP bodies. A separate proxy executable is an open question, not a design this project has accepted.
- A directory config is not merged with `~/.config/nsvault`.
- Shell completion does not list provider keys.
- AWS Secrets Manager, GCP Secret Manager, and Azure Key Vault were tested only against pinned local Floci emulators. The emulator does not validate AWS SigV4 signatures and does not prove production authentication, IAM, quotas, or regional behavior.
- Cloud credentials are static for the process lifetime. There is no AWS STS/IMDS chain, GCP ADC or service-account JWT exchange, Azure Entra ID or managed-identity flow, or token refresh.
- Azure Key Vault `ensure` is refused because there is no conditional create. Only the latest version is read.
- GCP Secret Manager `ensure` is refused because create and add-version are separate calls. A partial create could leave an empty secret, and a retry would report Present.
- GCP `allow_anonymous` is a loopback-emulator switch and is refused for any non-loopback endpoint.
- Windows and macOS were not exercised.
